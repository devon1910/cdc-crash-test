# M5: E3 connector-stopped experiment

E3 asks what the PostgreSQL slot and Debezium health endpoint show when Debezium stops while writes continue. The runner writes to both `public.orders` and `public.noise` at 10 inserts/second each for 10 minutes by default. At the halfway point it runs `docker compose stop debezium`, keeps writing and sampling, then restarts Debezium after the final stopped-state sample. It does not drop the slot, reset offsets, or remove volumes.

Run `make e3`. On Windows without GNU Make, run `go run ./cmd/e3`. For a setup check, use `go run ./cmd/e3 -duration=90s -interval=5s -settle=5s`; use the default duration for the milestone verdict. Keep the terminal open until the summary is written and the final “Debezium restarted after E3” message appears. If the process is interrupted after the stop, run `docker compose up -d debezium` to restore the lab.

Each run writes `results/e3/<timestamp>/observations.csv` and `summary.md`. The summary records when the stop was requested and completed, the last sample before the request, first sampled inactive slot, first non-UP health sample, the first completed-stop sample, and the first later sample whose retained-WAL distance exceeds that completed-stop baseline. It also reports pre-stop, completed-stop, and final LSNs and a post-stop WAL-distance growth rate. These times are sampling bounds, not exact instants when PostgreSQL changed state.

`confirmed_flush_lsn` may advance while Debezium is shutting down, so compare it at the first sample after the stop completed with the final sample before claiming it was stationary while stopped. A stopped Debezium process should make its health endpoint unreachable, while an inactive slot shows the replication client detached. Retained-WAL distance is the byte distance from current WAL to the slot's `restart_lsn`; it is not the physical `pg_wal` directory size. The runner makes no claim about data loss or a production disk filling.

## Verified full run (2026-09-28)

The 10-minute run [summary](../results/e3/20260928T104944.136Z/summary.md) and [raw samples](../results/e3/20260928T104944.136Z/observations.csv) recorded 5,999 committed rows in each table and 122 samples; the largest gap was 5.471 seconds. The stop request was at 10:54:44 UTC and completed at 10:54:46 UTC. The first inactive-slot and non-UP-health sample was at 10:54:49 UTC, about 5 seconds after the request. Retained-WAL distance first exceeded the completed-stop baseline at 10:54:54 UTC, about 10 seconds after the request. The completed-stop and final flush/restart LSNs matched; retained-WAL distance grew from 231,280 to 1,662,840 bytes, about 4,772 bytes/second over that sampled interval. The `pg_wal` directory remained 32 MiB because its file allocation is a different measure. Debezium was restarted, and its health endpoint returned `UP` after the run.
