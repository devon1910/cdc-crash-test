# M4: quiet-publication E1/E2 comparison

The question is whether an active heartbeat helps PostgreSQL release WAL when application writes are confined to `public.noise`, a table outside Debezium's publication. E1 disables heartbeats. E2 uses a 10-second Debezium heartbeat whose action query updates a one-row `public.cdc_heartbeat` table. Both runs publish `orders` and `cdc_heartbeat`, exclude `noise`, and produce no new `orders` rows from the runner.

`make e1` and `make e2` each run for 10 minutes by default at 10 noise inserts/second, sample the slot every 5 seconds, and wait 5 seconds after load for a final sample. On Windows without GNU Make, use `go run ./cmd/m4 -scenario=e1` and then `go run ./cmd/m4 -scenario=e2`. Run them sequentially; each command recreates the Debezium container with the corresponding configuration, but preserves its offset volume and the PostgreSQL data volume. It also performs an idempotent migration that creates and grants access to the heartbeat table and adds it to the existing publication. It never drops the slot, publication, volumes, or data.

For a quick setup check, pass the same `-duration=30s -interval=5s -settle=5s -rate=10` flags to both commands. Do not treat a short run as the M4 verdict. Results live under timestamped `results/e1/` and `results/e2/` folders; each contains raw `observations.csv` and a `summary.md`.

Compare the two runs' confirmed flush LSN, restart LSN, start/end/peak retained-WAL distance, health, sample gaps, and heartbeat update count. The key retention metric is distance from `restart_lsn` to current WAL, not the physical `pg_wal` directory size (which can remain allocated). A moving `confirmed_flush_lsn` with stationary `restart_lsn` is only partial progress; do not call that WAL-retention success. Different starting LSNs and WAL distances are expected because the runs occur sequentially. Compare changes and slopes, not absolute start positions. If health or sampling coverage fails, repeat the affected run.

The receiver does not currently prove end-to-end delivery for every row. This milestone evaluates source-side slot behavior, not a guarantee that a production CDC pipeline is safe. The active heartbeat design follows [Debezium 3.6 PostgreSQL connector documentation](https://debezium.io/documentation/reference/3.6/connectors/postgresql.html); see [ADR-005](adr/005-heartbeat-experiment-design.md) for tradeoffs.
