# M4: quiet-publication E1/E2 comparison

The question is whether a healthy Debezium slot can advance when application writes are confined to `public.noise`, a table outside Debezium's publication, and which heartbeat configuration helps it. E1 disables heartbeats. E2 timer-only sets `heartbeat.interval.ms=10000` with no action query. E2 active sets the same interval and uses an action query that updates a one-row, published `public.cdc_heartbeat` table. All variants publish `orders` and `cdc_heartbeat`, exclude `noise`, and produce no new `orders` rows from the runner.

`make e1` and `make e2` each run for 10 minutes by default at 10 noise inserts/second, sample the slot every 5 seconds, and wait 5 seconds after load for a final sample. On Windows without GNU Make, use `go run ./cmd/m4 -scenario=e1` and then `go run ./cmd/m4 -scenario=e2`. Run them sequentially; each command recreates the Debezium container with the corresponding configuration, but preserves its offset volume and the PostgreSQL data volume. It also performs an idempotent migration that creates and grants access to the heartbeat table and adds it to the existing publication. It never drops the slot, publication, volumes, or data.

For a quick setup check, pass `-duration=30s -interval=5s -settle=5s -rate=10` to each run. The timer-only variant uses `go run ./cmd/m4 -scenario=e2-timer`. Do not treat a short run as the M4 verdict. Each summary records the question, software versions, configuration, measured signals, and scenario-specific verdict.

Sequential runs preserve the PostgreSQL and Debezium volumes, so a later case can inherit the earlier case's slot backlog. For an independent comparison, `make m4-comparison` (or `scripts/run-m4-comparison.ps1`) asks for confirmation, deletes this Compose project's volumes before each of the three variants, and writes evidence to `results/m4-clean-comparison/`. This permanently removes the database, slot, and offsets in those volumes; it keeps result files. The measured comparison is documented in [M4 comparison results](../results/m4-comparison.md).

Compare confirmed flush LSN, restart LSN, start/end/peak retained-WAL distance, health, sample gaps, and heartbeat update count. The key retention metric is distance from `restart_lsn` to current WAL, not the physical `pg_wal` directory size (which can remain allocated). A moving `confirmed_flush_lsn` with stationary `restart_lsn` is only partial progress; do not call that WAL-retention success. For sequential runs, compare changes and slopes, not absolute start positions. If health or sampling coverage fails, repeat the affected run.

The receiver does not currently prove end-to-end delivery for every row. This milestone evaluates source-side slot behavior, not a guarantee that a production CDC pipeline is safe. The active heartbeat design follows [Debezium 3.6 PostgreSQL connector documentation](https://debezium.io/documentation/reference/3.6/connectors/postgresql.html); see [ADR-005](adr/005-heartbeat-experiment-design.md) for tradeoffs.
